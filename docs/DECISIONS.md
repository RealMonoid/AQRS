## Adaptive research integration

This maps the design adopted in ADR-045 to the actual AQRS milestone names and implementation. The [existing milestone gates](MILESTONE_DOD.md) and [experiment queue](MILESTONE_STATUS.md#experiment-queue) govern individual tests and their prerequisites.

Apply [Lean Build–Measure–Learn](DEVELOPMENT_PROCESS.md#feature-and-venture-experiments) to the integration. Once development data are qualified, start with one observable event, one matched control and one predeclared research decision. Reuse the existing evaluation, SQLite journal and Resource Governor where their contracts fit. Have the researcher make and record the decision. Use that workflow as the baseline for any later automation. Before building an automation increment, name an observed bottleneck and define how a bounded test will measure improvement. The protected evaluation gate applies before any real protected evaluation.

| AQRS gate | Target capability | Existing starting point and evidence needed |
|---|---|---|
| M1 — Data feasibility | Establish the source, observable events, availability and executable scope before forming a campaign. Keep development data separate from any independent confirmation set. | The source screen and conditional import pilot are already queued. Establish the market contract before selecting real event rules or costs. |
| M2 — Discovery | For a single event, record an economic rationale, a rival explanation, a matched control and the observation that would change the next decision. Keep room for unexpected structures and interactions without strong marginal effects. Record the scope and revisit trigger when parking a hypothesis. | Reuse `market.py`, `evaluation.py`, and the [event-defined research funnel](RESEARCH_PROTOCOL.md#lean-research-funnel) where their contracts fit. First test one synthetic decision. Later, compare a structured interaction with an additive baseline under matched inputs and use an XOR fixture and a null control before extending the search. |
| M3 — Research allocation | Prioritize experiments by the decisions their plausible outcomes can change. Use explicit scenarios when outcome probabilities are unknown. Keep bounded capacity for refinement, interactions and open discovery. Record what was tried, stopped, parked or reopened, with lineage. | Reuse `research.py` for the CLI flow, `journal.py` for attempt history, and `planning.py` and `governor.py` for limits. The current candidate order is fixed. Compare complete search policies in controlled replay against fixed ordering under equal budgets, including stopped attempts and selection distortion. |
| M4 — Independent confirmation | Evaluate a security boundary outside research-agent authority before any real protected evaluation. Freeze candidate, data scope and test rule. Give candidate code only time-eligible inputs, isolate it from the scorer and future outcomes, and restrict releases to predeclared outputs. Track exposure across candidates, campaigns and overlapping sources. | M0 passes a research prefix to the worker and writes the full synthetic series to `dataset.csv`. That demonstrates pipeline separation. See the [open isolation design question](OPEN_QUESTIONS.md#protected-evaluation-design) for the separate access-control evidence. |
| M5 — Strategy decisions | Carry the event, eligible population, horizon, controls, uncertainty, and cost and fill assumptions into a small strategy comparison that includes no trade. Test any policy derived from discovery on its own independent evidence. Report predictive, causal and economic claims separately. | Start from `evaluation.simulate` and its existing controls where execution assumptions match. Market-specific execution and independent strategy confirmation need their own evidence. |

The design treats EVSI, bandits, Bayesian optimization, causal discovery, and information-theoretic or neural interaction methods as conditional. Evaluate an individual method when a measured limitation of the simpler path could change a research decision and a bounded comparison is authorized. Recording this design adds no research work. Before each integration, estimate development time separately from recurring trials, fits, folds, seeds, resampling, runtime, memory and storage as applicable under the [Resource Governor](RESOURCE_GOVERNOR.md#resource-assessment-for-every-feature-proposal).

## Revision procedure

- Each new method begins with a **baseline** and explicit **acceptance criterion**.
- Exclude a research branch only based on **documented, evidence-backed, temporally revisitable** feasibility arguments.
- Reconsider priorities if data, market structures, costs or evidence change; record version and date.
- A failed final holdout does **not** authorize endlessly optimizing on the same final holdout.
- A native Windows **or** Linux compatibility failure is an open release blocker, not a documentation detail; WSL success alone cannot fulfill the Windows gate.
- When changing a machine contract, preserve identifiers when possible and version any migrations.
